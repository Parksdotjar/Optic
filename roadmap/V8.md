# Version 8 — Creator Workflow

## Main Goal

Let creators manage the capture stage inside Minecraft through profiles, a lightweight recordings library and useful naming/notes. Build on V5 presets, V6 clips and V7 metadata without turning Optic into a video editor or replacing the underlying recording engine.

## User Experience

A creator selects a profile, records normally, and later finds the recording by date or a meaningful name. The library offers Open, Rename, Open Folder, Delete and View Markers. Notes such as a video title and an editing reminder stay attached to the recording. The original Record/Stop flow remains available without using the library or creating a profile.

## New Features

- Profiles such as YouTube, Shorts, Cinematic, Low-End PC, High FPS and Custom.
- Profiles combine resolution, FPS, quality, audio tracks, clean-capture policy and preferred encoder using capabilities already implemented in earlier versions.
- An in-game recording/clip library with duration and grouping by date/session.
- Safe automatic naming templates, including `{date}`, `{server}` and `{time}`, plus lightweight recording notes.

## Technical Work

Add a versioned profile schema that references existing settings contracts. Resolve profiles to a concrete supported configuration before capture; retain user edits and show capability substitutions. Separate a user's intent from machine-specific resolved encoder choices so copying a profile between GPUs does not hard-code an unavailable backend.

Implement the library as an asynchronous bounded index of session manifests and finalized media. Support incremental refresh, filesystem reconciliation and paged loading. Do not scan/probe all videos or decode thumbnails on the render thread. Reuse V7 cached thumbnails and summaries; missing caches must not prevent listing recordings.

Treat rename and delete as operations on a recording bundle: video, tracks/sidecars, markers, thumbnails and metadata. Use stable IDs rather than filenames as identity. Serialize file operations with recording finalization/recovery; refuse operations on active or pinned V6 data. Handle external file moves and changes without deleting unrelated files.

Resolve filename templates with a small explicit token set, sanitize unsafe/reserved characters, prevent path traversal and add collision-resistant suffixes. A server token should use an optional display label, not expose a private address by default. Notes should be size-limited plain text, with atomic saves and schema migration.

Shorts is a profile name, not permission to promise a new camera/composition system: use only supported V5 aspect policies, explain cropping, and preserve readable output UI where relevant.

## Performance Work

Keep library indexing, file opening, probing and metadata edits off-thread. Recording hot-path code must not iterate library entries. Virtualize visible rows and bound thumbnail memory; background work should yield during active recording or storage contention.

Provisional targets: first cached library page within 250 ms on the reference dataset; unindexed directories show incremental results rather than freezing; UI actions acknowledge within 100 ms. Test at 10,000 entries. Cap thumbnail cache memory initially at 64 MiB and enforce explicit worker/queue limits. These targets are measured on declared storage/hardware, not universal latency promises.

With the library closed, stay within V7 benchmark noise. With indexing active during recording, investigate more than 5% p95/p99 frame-time regression or 3% 1% low regression; throttle indexing before reducing recording quality. Verify RAM plateaus and metadata growth is proportional to stored entries, not session duration while idle.

## UI / UX

Use a restrained list, date grouping and a compact detail page. Keep profile choice secondary to Record. Advanced profile fields remain behind Advanced. Open launches the user's normal player/editor where supported; do not build a timeline editor. Destructive actions require a clear, specific confirmation identifying the recording bundle. Prefer recoverable deletion where the platform supports it and state when deletion is permanent.

## Reliability

Atomic metadata writes, rename collision handling, file locking and partial bundle operations must preserve recoverability. Do not delete the only recoverable source while finalization is incomplete. A failed external-player launch should produce a concise error and keep Open Folder available. Corrupt or unknown-version metadata should not make the library unusable.

Known risks include external file changes, Unicode/path limits, symlink/path traversal, profile migration losing preferences, and background indexing competing with video writes. Resolve paths within the intended managed directory and never treat note/template text as a shell command.

## Compatibility

Use platform-aware filename and file-opening behavior. Preserve V1–V7 recordings and sidecars, including clips. Keep profiles portable across supported encoders by validating capabilities locally. Optional mods referenced by a profile may be absent; explain unavailable fields and never enable imaginary behavior.

## Testing Requirements

- Pass V1–V7 regression suites and decode recordings from older versions.
- Test 10,000-entry libraries, corrupt metadata, missing files, external renames and slow/network-backed folders where supported.
- Exercise rename/delete during finalization, clip export, recovery and an externally open player.
- Test templates with Unicode, reserved device names, path separators, duplicate timestamps and missing server labels.
- Migrate older settings/profiles and verify custom fields survive supported migrations.
- Measure indexing, scrolling and thumbnail loading while recording, including storage contention and p99 frame times.

## Completion Criteria

Creators can select a truthful profile, locate/open recordings, manage names and notes, and access markers without leaving Minecraft for capture administration. Operations preserve recording bundles and older media. Large libraries remain responsive and background work respects recording budgets.

## Explicitly Not Included Yet

No editing timeline, cuts/transitions, rendering finished YouTube videos, platform uploads, cloud accounts, collaboration, media transcoding farm or automatic framing. Profiles cannot expose capabilities deferred by earlier versions. No mandatory library interaction before recording.

## Notes for the Next Version

Provide V9 with extensible capability-aware profiles and bundle metadata for auxiliary outputs. Advanced codec/layer settings should extend Advanced rather than clutter simple profiles or make older recordings unreadable.
