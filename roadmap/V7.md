# Version 7 — Creator Markers

## Main Goal

Make long recordings easier to review and edit using optional timestamped metadata, without adding meaningful recording overhead or collecting unnecessary personal information. Preserve V6 full-recording and clip behavior.

## User Experience

Press configurable F7 to add a marker while playing. Start with a simple default marker and offer optional KEEP, FUNNY, IMPORTANT, B-ROLL, RETAKE and THUMBNAIL types. A short confirmation appears without pausing gameplay. After recording, a compact timeline lists events and optional notes; recording remains usable without markers.

## New Features

- Marker events with session ID, stable marker ID, media time, type and optional note.
- Optional Minecraft context: coordinates, dimension, local world/server label and relevant session/player information only when deliberately enabled.
- Asynchronous small thumbnails linked to markers.
- Generic CSV/JSON export, plus editor-specific adapters only after verified import testing.

## Technical Work

Create a versioned metadata sidecar and append/recovery strategy that reuses V2 session identities and V3 shared time. Record both monotonic event time and its mapping to encoded media time; wall-clock timestamps alone are insufficient. Preserve mappings through V6 clip rebasing, duplicates and missing capture intervals.

Snapshot lightweight Minecraft context on the appropriate game thread at keypress. Send immutable bounded events to a metadata worker. Notes and serialization run outside the render hot path. Marker failure must not block or invalidate video.

For thumbnails, reuse a completed capture frame or a separately budgeted GPU downscale/readback. Never take a synchronous full-resolution screenshot per keypress. Define what happens if the nearest frame was dropped or history has expired: label an approximate thumbnail or omit it. Rate-limit capture and bound thumbnail work separately from video buffers.

Use a portable internal schema and independent export adapters. Investigate Premiere, DaVinci Resolve and Final Cut XML formats against exact editor versions, rational frame rates and timecode rules. Do not imply that a generic CSV is directly importable as native timeline markers everywhere. Preserve Unicode, escaping, frame-rate metadata and stable ordering.

## Performance Work

Disabled markers must register no extra per-frame capture work. Marker input should only enqueue a bounded event. Proposed targets: acknowledgment within 100 ms, event handling below 0.2 ms p95 on the reference machine excluding optional thumbnail work, and no measurable regression beyond a 5% p95/p99 or 3% 1% low threshold during realistic marker use.

Stress bursts well above normal use. Rate-limit or omit thumbnails first; keep lightweight text markers while their bounded event budget permits. If the event queue fills, explicitly report the unsaved marker rather than silently losing it. Set a bounded thumbnail cache and disk budget, measured independently of recording storage.

## UI / UX

Use a small marker confirmation and a basic post-recording list with timestamp, type and note. Customization belongs in a secondary screen. Do not require selecting a category before every keypress. Recording/marker hotkeys must be rebindable, and confirmations must respect V4 indicator exclusion where supported.

Coordinates, server identity and thumbnails may reveal private information. Default contextual exports to the minimum needed, provide clear inclusion choices, and preview export fields. Avoid account tokens, server addresses or other players' details unless specifically needed and opted into.

## Reliability

Recover marker sidecars after interruption, tolerate an incomplete final event and keep video valid if metadata is damaged. Renaming or finalizing a video must not orphan its marker associations. A marker in expired replay history should not pretend that footage still exists.

Known risks: timecode rounding, duplicate timestamps, thumbnails exposing hidden chat, export format changes and private server metadata leakage. Tests must cover all of these before an adapter is labelled supported.

## Compatibility

Keep context extraction in Minecraft adapters and export formats independent of Minecraft. Preserve all V1–V6 track, clean-capture and clip options. Editor support is a tested format/version matrix, not an unconditional brand-level promise. No external editor installation is required for ordinary recording or generic metadata export.

## Testing Requirements

- Pass V1–V6 functional and performance regressions.
- Compare marker timing to known frame events at 30/60/120 FPS, during frame drops and across clip rebasing.
- Exercise Unicode notes, CSV/XML escaping, duplicate markers, empty notes and large sessions.
- Crash while appending metadata or writing a thumbnail; verify recovery without modifying video.
- Import each offered editor-specific format into its declared editor version and verify timing within one output frame.
- Check optional context redaction and that thumbnails obey supported V4 recording visibility policy.

## Completion Criteria

Markers reliably identify the intended media moment, metadata survives interrupted sessions, supported exports import correctly, and disabled/ordinary marker use meets performance gates. Context collection is optional and clearly described. Unverified editor integrations remain planned or unavailable.

## Explicitly Not Included Yet

No automatic highlight scoring, transcription, face/player recognition, clip editing, collaborative annotation, cloud synchronization or full playback editor. Do not collect extensive player/session data just because Minecraft exposes it.

## Notes for the Next Version

Provide V8 with stable media/marker identities, rename-safe references, lightweight summaries and a bounded thumbnail cache. The future library should index these artifacts rather than parse entire recordings or load every thumbnail at startup.
