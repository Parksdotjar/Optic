# Version 4 — Clean Capture

## Main Goal

Allow useful information to remain visible to the player while selected supported elements are absent from the recording. Extend the existing capture pipeline without routinely rendering the world a second time. This is a rendering feasibility and correctness milestone, not permission to promise arbitrary mod-overlay removal.

## User Experience

The player can keep chat, navigation and recorder feedback on screen while exporting clean footage. A small Capture Elements page offers separate supported switches for Minecraft HUD, chat, player names, recording indicator, debug display and compatible waypoints. Changes clearly state whether they take effect immediately or on the next recording.

## New Features

- Independent player-visible and recording-visible policies for supported render elements.
- Granular built-in policies for chat, subtitles, scoreboard, boss bars, action bar and debug information where render ordering allows it.
- Optional adapters for supported waypoint, minimap, performance and Flashback overlays.
- A capability report that distinguishes supported exclusion, unsupported elements and conflicts with another rendering mod.

## Technical Work

Map the actual 1.21.11 render ordering before choosing hooks. Separate screen-space UI from world-space content such as player nameplates; they cannot be assumed to share a cheap interception point. Identify when the current final framebuffer loses the information needed for selective capture.

Introduce a small capture-visibility policy and render-layer adapter interface near the version-sensitive hooks. Use a frame-boundary snapshot of policy rather than querying mutable settings repeatedly during draw calls. Preserve V2 session ownership and V3 clocks/tracks.

Compare capture before a supported overlay pass, compositing selected UI into a recording target, and separating reusable overlay draw commands. A pre-HUD snapshot supports all-HUD exclusion but does not automatically support arbitrary include/exclude combinations. Replay of draws must not trigger UI side effects twice, duplicate animation updates or retain frame-local resources beyond their lifetime.

Prototype minimal extra targets/copies only when necessary. Do not reconstruct hidden world pixels by erasing a finished image. World-space exclusions may require an earlier render hook; explicitly defer them if a correct low-cost path cannot be established. Keep player rendering unchanged after any adapter failure.

## Performance Work

Benchmark each exclusion mode against V3 at the same output quality and resolution. Count world renders, texture copies, GPU passes, VRAM growth and CPU hook cost. Treat every additional per-frame pass as expensive until measured. Never perform CPU scaling or synchronous screenshot readback for this feature.

Targets: default/no-exclusions mode adds no new world pass or frame-sized copy; basic clean-HUD mode should require zero additional world renders. Proposed incremental CPU budget for basic exclusion is at most 0.2 ms p95 on the reference machine, with a separately published GPU/memory cost. Investigate more than 5% p95/p99 frame-time regression or 3% reduction in 1% lows on supported clean presets. Expensive modes must not become defaults merely because they are technically possible.

## UI / UX

Use compact ON/OFF rows under an optional Capture Elements page. Explain that settings affect the video, not the player's screen. Parent HUD settings and child elements must have unambiguous precedence. Mark unsupported controls unavailable rather than leaving toggles that do nothing. A preview is optional and on demand; do not continuously duplicate rendering to show it.

## Reliability

Fail an incompatible clean-capture request explicitly; never silently advertise excluded content as absent. If an adapter fails mid-session, stop or clearly notify according to a documented policy, preserving footage. Do not expose private chat in a supposedly clean output without warning. This is best-effort visual composition, not a privacy/security boundary against arbitrary mods.

Known risks include deferred rendering APIs, overlay order changes, shared draw state, shaders that compose UI differently, and world-space labels already baked into the scene. Preserve GL state and validate resource lifetimes in each adapter.

## Compatibility

Investigate Xaero, JourneyMap, waypoint mods, Flashback, performance overlays and shader/rendering mods individually. Public integration points are preferred. Publish exact tested combinations; do not infer compatibility from one mod's screen position. Missing or unsupported optional mods must not affect ordinary capture. Keep the existing vanilla-style pause controls and collision handling.

## Testing Requirements

- Pass all V1–V3 functionality, audio sync, recovery and lifecycle tests.
- Compare player screenshots and decoded video for every supported element and representative combinations.
- Exercise chat arrival, boss fights, subtitles, debug toggling, scoreboard updates, UI scaling and window resizing.
- Test overlays absent/present, different registration order, shader reload and resource reload.
- Confirm no duplicate UI side effects and no second world render in basic clean mode.
- Measure disabled, simple clean and worst supported combination frame-time distributions, including 1% lows and GPU passes.

## Completion Criteria

Supported controls demonstrably affect only the intended output, the player retains requested UI, basic clean capture meets the no-second-world-render constraint, and performance budgets pass on declared configurations. Compatibility failures are visible and recoverable. Every deferred element is labelled accurately.

## Explicitly Not Included Yet

No arbitrary pixel removal, automatic censorship, guaranteed exclusion of unknown overlays, additional camera views or replay rendering. No routine second world render. Depth/entity auxiliary exports belong to V9; broad resolution-pipeline optimization belongs to V5.

## Notes for the Next Version

Give V5 explicit composition stages, target ownership and measurable copy/pass counts. Resolution optimization must preserve the difference between player and recording visibility and avoid discarding proven clean-capture behavior.
